上一篇把基于表单的暴力破解跑通了，我本来以为第二关无非是登录框底下多一张验证码，照着再来一遍就行。结果第一次把字典跑完，二十条请求整整齐齐全是「验证码输入错误」，一条都没走到密码那一步。

这一关是重做了一遍的，截图也是这一遍里截的，下面按实际操作的顺序记下来。实验还是在自己的虚拟机内网里完成，没有碰公网或者别人的站点。

| 角色 | 用的东西 | 说明 |

## 二、先弄明白几个东西

### 页面和请求多了什么

页面跟上一篇长得差不多，就是登录框下面多了一行验证码：一张图片加一个输入框。

抓包看请求，路径从 `bf_form.php` 变成了 `bf_server.php`，请求体也从三个参数变成四个：

```text
POST /pikachu/vul/burteforce/bf_server.php

username=admin&password=123456&vcode=6do6vc&submit=Login
```

多出来的 `vcode`，就是把图片上那几个字符填进去提交的值。

### 验证码存在哪儿

验证码不是写死在页面里的。要是写在前端，右键看源码就能拿到答案，那它也就没什么意义了，所以它存在服务器那边的 session 里。

session 我是这么理解的：HTTP 本身不记事，服务器处理完一个请求就把你忘了。所以第一次访问时它会发给你一个编号（就是 Cookie 里的 `PHPSESSID`），自己那边留一个柜子，编号一样，柜子里就存着你这次的状态——登录没有、验证码是多少。之后你每次带着编号去，服务器就知道该开哪个柜子。

校验顺序大概是这样：

```text
if (提交的 vcode == session 里的 vcode) {
    继续查数据库，校验账号密码
} else {
    直接返回「验证码错误」，密码那一关根本不执行
}
```

也就是说先过验证码、再验密码。验证码对不上，你连试密码的资格都没有——这正是我第一次全军覆没的原因。

还有一点后面会用到：Burp 只发我们让它发的请求，不会像浏览器那样自动去加载页面里的验证码图片。所以只要手里有一个当前有效的 vcode，并且不再去刷新页面，这个值就不会被换掉。

## 三、实验步骤

### 3.1 按上一篇的做法直接跑

先照搬上一篇：右键请求 → Send to Intruder，攻击模式用 Sniper，只把 `password` 那一段加 §，`vcode` 保持抓包时那次的值不动，字典还是那二十条常见密码，Payload type 选 `Simple list`：

![第一次的 Intruder 配置：只有 password 被标记，vcode 用的是抓包时的值](/img/pikachu-02-first-config.png)

### 3.2 二十条全被挡回来

跑完结果很整齐：二十条的响应长度全是 35378，一模一样。随手点开一条看 Render，页面上写着「验证码输入错误哦！」：

![第一次结果：所有请求都返回验证码输入错误](/img/pikachu-02-all-failed.png)

一开始我还以为是字典的问题，换了一份还是全错。停下来想了想才反应过来：字典跟验证码压根不是一回事，密码根本没被校验，请求在第一道关就被打回来了。

### 3.3 找到真正的问题

对比两次截图能看出一个细节：抓包那会儿请求里的 `vcode` 和页面图片上显示的验证码已经不是同一个了。验证码图片每被浏览器加载一次，服务器就会生成一个新的，把柜子里旧的那个覆盖掉。等我回到 Burp 里重发那条旧请求，手里这张票早就作废了。

所以要做的不是换字典，是换一张**当前有效**的票。页面上此刻显示的验证码是 `6do6vc`，我把它填进请求里的 `vcode` 再发一次：

![把 vcode 换成页面当前显示的验证码后，返回变成「用户名或密码不存在」](/img/pikachu-02-page.png)

这次返回的不再是「验证码输入错误」，而是 `username or password is not exists`。这句话挺关键的：说明验证码这一关已经过了，服务器真的去查了账号密码，只是我填的密码不对。

### 3.4 固定 vcode 再跑一次

回到 Intruder 的 Positions，把 `vcode` 固定成 `6do6vc` 并且**不加 §**，只让 `password` 带 §，字典还是那二十条：

```text
username=admin&password=§123456§&vcode=6do6vc&submit=Login
```

![修正后的 Positions：vcode 固定，只有 password 带 §](/img/pikachu-02-positions.png)

这里有个操作上要注意的地方：跑之前把浏览器那个页面关掉，或者至少别再去刷新它。一刷新，浏览器就会重新加载验证码图片，服务器换票，跑到一半又会全部变成「验证码错误」。Burp 自己不会加载图片，所以只要不去碰页面，这二十条请求用的就都是同一张有效票。

点 Start attack，二十秒左右跑完。

## 四、结果与分析

按 Length 排一下，十九条都是 35374，只有 `123456` 那条是 35351。点开 Render，写着 `login success`：

![第二次结果：长度异常的那条 Render 显示 login success](/img/pikachu-02-success.png)

| 验证项 | 第一次 | 修正后 |
|---|---|---|
| vcode | 抓包时的旧值，已失效 | 固定为页面当前显示的 `6do6vc` |
| 密码位置 | password 加 § | password 加 §（不变） |
| 响应长度 | 20 条全是 35378 | 19 条 35374，`123456` 那条 35351 |
| 页面提示 | 全是「验证码输入错误哦！」 | `login success` |

能这样跑通，说明同一个验证码被连续用了二十次都没失效。验证码确实是在服务端校验的，位置没放错，问题在于它只在页面加载时生成一次，提交之后不管成功失败都不销毁，等于一张门票能刷无数次。

正确的做法应该是「一次性」：不管校验结果如何，用完立刻作废，下次必须重新领一张。验证码的防线本来就不在于「你猜不到下一张是什么」，而在于「你手里这张只能用一次」。这一点没做到，整套防护就跟没有差不多。

## 五、如果我是开发，怎么防

- 验证码校验完立刻销毁，别留在 session 里等下次再用。
- 给验证码加个有效期，超过一两分钟就失效，别让它一直有效。
- 同一个 session 连续失败几次就锁定，或者强制重新获取验证码。
- 登录失败的提示统一措辞，别让页面告诉攻击者太多信息（比如到底是哪一项错了）。

## 六、小结

这一关花时间最多的不是爆破本身，而是想明白「为什么二十条会整整齐齐全错」。做完之后印象最深的有两点：一是技术上，验证码安不安全，关键不在图有多难认，而在用完就作废；二是操作上，批量跑之前先拿一两条请求把机制确认清楚，比对着一屏一模一样的错误发呆省时间得多。

和上一篇对着看也挺有意思：加了验证码，看起来比第一关严了，但因为验证码能反复用，最后还是被同一份二十条的小字典跑出来了。
