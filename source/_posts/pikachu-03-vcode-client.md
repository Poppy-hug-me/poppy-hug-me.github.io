前两关一关比一关费劲，我以为第三关会更头疼。结果这一关反而是三关里最快的，因为它压根没打算防住工具。

这一关是验证码绕过（on client）。页面跟上一篇几乎一模一样，区别只在验证码放到哪一端去校验。实验还是在自己的虚拟机内网里完成，没有碰公网或者别人的站点。

## 一、实验环境

| 角色 | 用的东西 | 说明 |
|---|---|---|
| 靶机 | VMware 里的 Windows 10 + phpStudy + Pikachu 源码 | 跑着带漏洞的网站 |
| 攻击机 | Kali Linux + Burp Suite 社区版 | 抓包、重放、批量发请求 |
| 网络 | VMware NAT，两台机器能互相访问 | 和公网隔开 |
| 本关页面 | 暴力破解 → 验证码绕过（on client） | 页面跟上一篇几乎一样，校验位置不同 |

环境跟上一篇完全一样，只是换了关卡，所以工具不用重新配。

## 二、先弄明白几个东西

### 2.1 页面与请求的差异

页面跟上一篇长得差不多，登录框下面照样是一张验证码图片加一个输入框。

但这次我留意了一下地址栏，路径从 `bf_server.php` 变成了 `bf_client.php`。

server 和 client，这个命名基本已经把答案写在了脸上——验证码的校验到底放在哪一端。上一关是服务器替我核对，这一关多半是浏览器自己核对。

### 2.2 客户端校验的含义

如果校验真的写在前端，那它对抓包工具就是透明的。浏览器点提交时会先跑一段 JS 挡一下，但这段代码只存在于浏览器里；用工具直接把 POST 发给服务器，它连执行的机会都没有。

这一点留到第四节再说，先按实验顺序把过程记下来。

## 三、实验步骤

### 3.1 直接把请求送进 Repeater

我先把两条请求（一条密码错的、一条密码对的）都送进 Repeater，`vcode` 也懒得抄图上的，随手填了个假值 `00000`，发出去。

![vcode 填成 00000，密码正确时仍然返回 login success](/img/pikachu-03-first-repeater.png)

结果两条请求都没有报验证码错误：密码错的那条返回「用户名或密码不存在」，密码对的那条直接 `login success`。

### 3.2 反常现象：图片在换，请求仍然通过

继续多按了几次 Send，我发现每次响应页面底部的验证码图片都不一样。第一反应是：完了，是不是又踩了第二关的坑，服务器在换票。

仔细看了一下才发现不对：我提交的 `vcode` 一个字都没改，几次用的都是同一个值，几次全过了。

也就是说，页面上的图片在变，跟手里这张票有没有效，完全是两件事。图片是服务器画给你看的，票有没有效是服务器自己说了算。而在这一关，服务器压根没算。

### 3.3 三组对照实验

光凭「没报错」还不够，容易是巧合。我做了三组对照，每次只改一个变量：

| 实验 | 输入 | 返回 | 说明 |
|---|---|---|---|
| 1 | 正确密码 + 假验证码 `00000` | `login success` | 假验证码没能拦住 |
| 2 | 错误密码 + 假验证码 `00000` | 用户名或密码不存在 | 报的是密码问题，**没提验证码** |
| 3 | 错误密码 + 删掉 `vcode` 参数 | 用户名或密码不存在 | 服务器连这个字段都没读 |

![错误密码配上假验证码 00000，返回的是密码错误，不是验证码错误](/img/pikachu-03-fake-vcode.png)

![把 vcode 参数整个删掉，返回依旧是密码错误](/img/pikachu-03-no-vcode.png)

第二个实验是关键。如果服务端真的在验验证码，它应该在查密码之前就把我拦下来，报「验证码错误」。结果它直接跳到密码判断，说明验证码那一步在服务端根本不存在。

第三个更直接：参数都不传了，请求照样往下走到查密码那一步，等于这个字段对服务器完全透明。

做实验的时候记住一个原则：**一次只改一个变量，用不同输入反推内部逻辑**。比单纯说一句「我绕过了」要有说服力得多。

### 3.4 用 Intruder 完成爆破

既然 `vcode` 删了也不影响，这次配置比上一篇还省事：直接把它从请求里去掉，只给 `password` 加 §，字典还是那二十条常见密码，Payload type 选 `Simple list`。

```text
username=admin&password=§123456§&submit=Login
```

点 Start attack，二十条很快跑完。按 Length 排序，只有一条跟别人不一样：

![Intruder 结果：Length 36562 的那条 Render 显示 login success](/img/pikachu-03-intruder-result.png)

## 四、结果与分析

### 4.1 校验实际发生在客户端

`vcode` 填假值能过、删掉也能过，说明服务端从头到尾没读过这个字段。那校验只可能在前端 JavaScript 里：点提交时，JS 先拿输入框的值和图片上的值比一下，不对就弹提示、阻止表单提交。

问题在于，这段代码跑在**你自己的浏览器**里。Burp 发请求的时候根本不经过浏览器，直接把 POST 甩给服务器，那段 JS 连执行的机会都没有。

所以这一关的漏洞不是「验证码能被我猜出来」，而是「验证码从来没在服务器上校验过」。前端校验只挡住了不会用工具的人，对会发原始请求的人来说等于没挡。

### 4.2 三关横向对比

做完三关，暴力破解的防护和绕过基本能串起来了：

| 关卡 | 防护手段 | 漏洞在哪 | 绕过方式 |
|---|---|---|---|
| 第一关 | 没有 | 没有 | 直接爆破 |
| 第二关 | 服务端验证码 | 校验后不销毁，可重复使用 | 固定一张有效票 |
| 第三关 | 客户端验证码 | 服务端根本不校验 | 用代理工具直接发请求 |

一条线下来很清楚：防护加在哪里不是关键，关键是**那道门有没有真的锁上**。

## 五、如果我是开发，怎么防

- **验证码必须在服务端校验。** 前端校验只能当体验优化，比如输错了立刻给个红字提示，但绝不能用它来决定放不放行。
- **服务端校验完立刻销毁。** 别留在 session 里等下次再用。
- **不要信任任何来自客户端的东西。** 隐藏字段、JS 变量、前端算出来的值，全都可以被改。

最后这条是个通用原则：**客户端提供的一切数据都是不可信的**。前端能做的隐藏、加密、校验，攻击者手里有工具，全都能看穿。

## 六、小结

这一关最快，但结论最硬：前端校验等于没有校验。

三关连着做下来，印象最深的是防护「写在哪一端」这件事。第一关什么都没有，第二关加了验证码但没作废，第三关看着有验证码，实际上只是给页面加了张图。表面上防护一层层加厚，实际上一次都没锁上。
